# i18n 工程规范

## 目标与适用范围

本文为 game-dapp-starter 定义适用于 Next.js App Router、vinext、Cloudflare Workers 与 Web3 DApp 的长期国际化工程规则。

本文负责 Locale ownership 与 resolution、Server / Client 一致性、translation resource ownership、API / Web3 error localization、数字与时间展示、翻译语法、多语言布局、persistence、missing translation 与 i18n QA。

目录归属与依赖方向遵守 docs/architecture.md；React、Tailwind 与 accessibility 实现遵守 docs/frontend-rules.md；API、Web3、State、Cloudflare、Design System、Figma 和 QA 的专项规则仍由对应文档负责。

## Baseline 与实施验证

next-i18next、i18next 与 react-i18next 是 docs/tech-stack.md 中的 Baseline direction，但：
~~~text
Baseline
≠ 当前一定已安装
≠ 当前一定已完成 Runtime 验证
~~~

实施 i18n 前必须检查当前 package、source code 与 config，不得仅根据本文假设某个 library、Provider、locale route、Cookie 或 resource structure 已存在。

当前 Runtime 为：
~~~text
Next.js App Router
→ vinext
→ Vite
→ Cloudflare Workers
~~~

具体实现只有完成 dev、build、Workers runtime、Server Component、Client Component、locale switch 与 hydration 的最小验证后，才能锁定为 starter 默认方案。upstream capability 不等于当前 vinext + Workers 链路已验证；不得将未经验证的 initialization pattern 固化为永久规则。

## Locale Ownership 与 Resolution

同一 request / render cycle 必须只有一个 authoritative resolved locale：
~~~text
one locale fact
→ one authoritative resolved locale
~~~

URL、Cookie、User Profile、browser language、localStorage、Zustand、i18n runtime 与 Client state 可以分别承担 explicit selection、preference、resolution input、persistence、transport、runtime representation 或 fallback candidate，但不得彼此竞争 source of truth。

Locale 不是普通 Local UI State：

~~~text
locale
≠ random useState
≠ arbitrary Zustand field
~~~

它影响 Server / Client render、translation resource、navigation、metadata、number / date formatting、accessibility text、hydration，以及可能的 URL。

每个项目必须集中定义、稳定执行并可测试 locale resolution policy。可能的输入包括：

~~~text
explicit route locale
explicit user selection
user profile preference
server-visible persisted preference
browser / request preference
project default locale
fallback locale
~~~

本文不规定固定 precedence；URL、Cookie、profile、browser 与 default 的优先级属于项目决策，不得由不同页面各自猜测。

通常，Route / URL 适合 shareable locale、SEO 与 locale-specific navigation；Cookie 适合 Server 可见 preference；User Profile 适合登录后的跨设备 preference；browser preference 适合首次 detection input，不能持续覆盖用户显式选择；localStorage 只能是 Client persistence source，不能成为 Server request locale owner。

supported locales、default locale 与 fallback locale 必须作为项目级集中配置；locale identifier 必须统一，例如 en、en-US、zh-CN、zh-TW 或 ja-JP。不得混用 zh、zh-cn、zh_CN、cn、Chinese 等表达同一 locale。

## Server / Client 一致性

currentLocale 属于 request-specific fact。Next.js / Cloudflare Workers Runtime 可能复用 module instance，因此不得通过 module-level mutable variable、global singleton 或 isolate 生命周期级状态跨请求保存当前 locale。

首屏必须满足：

~~~text
Server resolved locale
=
Client initial locale
~~~

Client 初始 translation resource 必须对应同一个 locale。必须防止：

~~~text
Server renders locale A
↓
Client initializes locale B
↓
hydration mismatch / wrong-language flash
~~~

Client 不得在首次 mount 时用 localStorage 覆盖 Server 已解析的 locale；初始值应来自同一 request context 或明确约定的 bootstrap，用户主动切换后才进入 locale transition。

不得将 wrong-language flash 当作默认体验，也不得为规避它而在 Client mounted 前隐藏整个本可 Server Render 的 App。

Server Component 应能以当前 request locale 生成文案；Client Component 应消费相同 resolved locale。若未来需要 i18n Provider，它必须位于最小合理 Client boundary，不得为了 i18n 将整棵 App 或大量 Server Component Client 化。具体 Provider、resource hydration 与 Server / Client API 仍须真实验证。

若项目启用 locale-aware metadata，title、description 与 OpenGraph text 必须与 resolved locale 一致。locale route、hreflang、domain locale 与 SEO architecture 只有在真实产品需要时设计。

## Translation Resource Ownership

translation ownership 应尽量与 application ownership 对齐：

~~~text
shared/i18n
→ locale resolution、基础 infrastructure 与无业务语义能力

shared/ui
→ 通用 UI 文案

domains/<name>
→ 稳定领域概念文案

features/<name>
→ workflow / action 文案

page-local
→ 页面局部文案
~~~

这不要求预建目录或资源文件；不得为了 i18n 创建一套与 Shared、Domain、Feature 平行且不一致的业务架构。

Translation key 应稳定、可读、有 owner，并表达 semantic meaning：

~~~text
swap.insufficientBalance
wallet.connect
transaction.pending
~~~

避免无意义编号、完整英文句子或 JSX tree path，例如 msg_10034、"Insufficient balance"、home.header.left.button.label。布局重构不应导致 key 大规模漂移；优先采用 owner + semantic meaning。

若使用 namespace，粒度应与 ownership、Feature boundary 和 Domain boundary 一致。不得形成 giant common.json，或 common2、misc、other、new、temp 等无 owner namespace；也不得机械地每个 React Component 一个 namespace。

~~~text
translation ownership
≈ application ownership
~~~

先保证 owner 正确，再根据真实 bundle 与性能证据选择 full resource、route-level、namespace-level 或 lazy loading。Server / Client 共用资源时，必须避免无意将全部语言和 namespace 打进 Client bundle。

## UI Copy 与业务语义

启用 i18n 后，稳定且用户可见的 button、label、title、description、empty state、error text、success feedback、dialog copy、aria-label 与 accessible name 不应继续大量散落硬编码。

translation resource 不等于 business data。token name、pool name、campaign title、user-generated content 与 Backend entity name 仍由真实 owner 提供。developer log、internal identifier、code enum、test fixture、protocol symbol、contract address、wallet address 与 tx hash 通常不应机械翻译。

ETH、SOL、USDT、Ethereum、Solana 等通常保持协议或产品官方名称；Connect Wallet、Switch Network、Transaction Pending 等属于 UI copy，应本地化。

Backend message 不等于最终 localized UI copy：

~~~text
Backend error code / semantic
↓
Feature interpretation
↓
translation key
↓
localized UI
~~~

只有真实 API Contract 明确 message 已本地化且允许直接展示时才例外使用。

遵守 docs/api.md：

~~~text
shared/api
→ error kind / status / backend code / context

Feature / consumer
→ business interpretation
→ translation
→ UI feedback
~~~

shared/api 不得调用 t()、Toast 或决定最终用户文案。machine-readable API 也不得仅因 UI locale 自动改变核心 data contract；Accept-Language、locale header 或 localized response 必须由真实 Contract 明确。

遵守 docs/web3.md：generic Web3 layer 保留 User Rejected、Unsupported Chain、Simulation Error、Broadcast Error、On-chain Revert、Backend Reconciliation Timeout 等 semantic error。Feature 决定 translation key、反馈与 UI；generic Web3 不得内置中文 / 英文业务提示或 Toast copy。

## Number、Amount 与时间本地化

DApp 必须严格区分：

~~~text
business value
≠ localized display

exact calculation
≠ formatting
~~~

展示层可以使用 Intl.NumberFormat 或等价能力处理 grouping、decimal display、percentage、compact 与 fiat display。但 BigInt、BigNumber、raw amount 与 exact decimal string 不得为格式化而转换为不安全的 JavaScript Number。

必须区分 plain number、token amount、percentage 与 fiat currency。1,234.5678 ETH 不是 USD currency formatting，不得因使用 Intl.NumberFormat 自动套用 fiat semantics。

localized display 不等于 transaction input：

~~~text
user input string
↓
normalize
↓
exact decimal
↓
raw unit
~~~

不得将 formatted display string 直接解析为 blockchain amount。若项目允许 localized amount input，必须定义 accepted separator policy、normalization rule 与 invalid format behavior；Global starter 不锁定具体 UX。

展示层优先使用 Intl.DateTimeFormat、Intl.RelativeTimeFormat 或等价能力，但必须区分：

~~~text
timestamp
timezone
locale
~~~

locale 不等于 timezone。locale 只决定 display convention，timezone 决定时间解释或展示区域；日期本地化不得改变真实 timestamp semantic，翻译字符串也不得参与业务时间计算。

## Translation Grammar 与安全边界

plural 必须由最终 i18n library 的 plural capability 处理，不得把 count === 1 ? "item" : "items" 推广为全局 grammar。

动态 amount、token、count、name 等应作为 interpolation 参数传入，由 translation resource 控制完整语序。不得拼接英文式句子：

~~~text
t("received") + amount + token
~~~

含 link、bold text、amount、inline component 或 button-like action 的文案，应使用安全的 component interpolation 或 composition。translation resource 不等于 trusted HTML boundary；不得因为字符串来自 locale file 就使用 raw HTML 或 dangerouslySetInnerHTML。

## Figma、Layout 与 Accessibility

多语言 Figma Frame 可用于检查 text expansion、wrapping、button width、component height、layout difference 与 PC / H5 behavior，但 Figma text 不等于 runtime translation resource source of truth。

单语言 Figma 不代表其他 locale 一定 fit。实现应考虑 longer text、CJK、long error message、long button label、line wrapping 与 overflow。普通 UI copy 不得用 ellipsis 掩盖 translation layout 问题，除非 Product / Figma 明确允许；wallet address、tx hash 与 identifier 的截断仍属于数据展示规则。

aria-label、accessible name、alt 与 screen reader text 都属于用户可理解的本地化内容。装饰性图片仍应遵守正确 accessibility 语义。尽量避免将可翻译 UI copy 烤进 raster image；若品牌插画确有文字，可由项目设计决定 locale-specific asset。

## Persistence、Preference 与 RTL

~~~text
locale
≠ auth
≠ wallet
≠ chain
≠ theme
~~~

未登录用户也需要 locale；User Profile 可以成为登录后的 preference input，但 logout 不默认 reset locale。wallet connect、disconnect、account switch 与 chain switch 不得默认改变语言。language 与 theme 可以共享 persistence infrastructure，但不得合并成含义模糊的 preference state。

若项目持久化 locale，必须明确 storage、scope、precedence、SSR visibility、migration 与 cleanup。locale 通常不是 Secret，但 persistence 仍须满足 Server / Client ownership 与 hydration 一致性。

starter 不要求预实现 RTL，也不得永久假设所有 locale 为 LTR。若项目支持 RTL locale，direction、layout、icons 与 spacing 必须成为真实 Design / Frontend requirement。

## Missing Translation、Fallback 与 AI Translation

Development 中 missing translation 必须可发现：

~~~text
missing key
≠ success
~~~

禁止 missing key silently 输出空字符串。fallback locale 可以避免 UI 空白，但 fallback rendered 不等于 translation complete；QA 必须能识别 fallback leakage。

AI 可以协助 draft translation，但 AI generated text 不等于自动批准的 production copy。financial copy、risk warning、security warning、irreversible action、transaction confirmation 与 legal copy 必须经过真实项目流程确认。

## i18n QA Boundary

i18n 规范至少要求验证：

~~~text
missing translation
fallback leakage
Server / Client locale consistency
language switch
long text
number formatting
amount input
date / timezone display
plural / interpolation / rich text
accessibility copy
PC / H5
important states
~~~

具体 test tooling、visual regression、device matrix、CI 与 test command 由 docs/qa.md 定义。

## Forbidden Patterns

- random page useState → application locale source of truth；
- Server locale A → Client locale B；
- browser language → overwrite explicit user preference every load；
- all translations → giant common.json；
- translation key → JSX tree path；
- Backend message → final localized UI；
- shared/api → t() + Toast；
- generic Web3 → localized business copy；
- BigInt / BigNumber → Number for localization；
- localized display → raw transaction amount；
- locale → timezone；
- translation string → dangerouslySetInnerHTML；
- missing key → empty string；
- i18n Provider → entire App Client Component。

## 实施检查清单

1. 当前 request 是否只有一个 resolved locale？
2. Locale resolution policy 是否集中、明确且可测试？
3. Server / Client 首屏 locale 和初始 resource 是否一致？
4. 是否存在 module-level mutable currentLocale？
5. resource 是否有明确 owner，且未形成 giant common namespace？
6. Key 是否表达语义，而非 UI position 或完整英文句子？
7. Backend、API 与 Web3 是否错误承担 UI 翻译？
8. localization 是否破坏数值精度，或混淆 amount input 与 display？
9. locale 是否与 timezone、auth、wallet、chain 或 theme 混淆？
10. plural、interpolation 与 rich text 是否避免英文式拼接和 raw HTML？
11. accessible copy、missing key 与 fallback leakage 是否可发现？
12. Client bundle 是否无意包含所有语言资源，或 i18n 是否导致过度 Client 化？
13. 当前方案是否已经在 vinext + Workers 中完成真实最小验证？
